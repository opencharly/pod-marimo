# 2026.321.1706 — chore(pins): require layer-cuda at the driver-strip release

## Summary

The `require:` in this candy is the one whose comment explains why a pod must not sit on an old GPU
pin — and it was itself the cause of exactly that failure, because `box/versa` composes this pod
beside its own `layer-cuda` pin:

```
$ charly box validate            # opencharly/distro-cachyos, box/nvidia-cdi cutover branch
validation error: candy github.com/opencharly/layer-cuda resolved to multiple git tags with differing
content within one scope (box=versa-cdi); using newest referenced v2026.321.1520
```

`pod-marimo:v2026.320.2210` names `layer-cuda:v2026.320.2103`, the release **before**
opencharly/layer-cuda#22 — the one that strips the host-coupled driver user-space that installing
`cuda` reinstalls through `nvidia-utils`, so the CDI injection is the only provider of the driver.
With that release merged and tagged (`v2026.321.1520`), this requirement advances:

```
layer-cuda:v2026.320.2103 -> v2026.321.1520
```

**Why it matters.** On the previous release a GPU container resolved `libnvidia-ml.so.1` to the image's
baked `620.70.06` instead of the injected host `615.78.08`, so `nvidia-smi` exited 18 with
"Driver/library version mismatch" and NVML consumers — ollama among them — silently ran on CPU
(opencharly/layer-cuda#21, fixed by #22). A pod that composes the CUDA stack should not pin a release
that reintroduces it, and the comment in this file now names both fixes it depends on.
